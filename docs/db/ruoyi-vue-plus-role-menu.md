## 1. `sys_role_menu` table

### 1.1 DDL (all four dialects shipped in `script/sql/`)

MySQL — `script/sql/ry_vue.sql:363-370`:

```sql
-- ----------------------------
-- 7、角色和菜单关联表  角色1-N菜单
-- ----------------------------
create table sys_role_menu (
    role_id   bigint(20) not null comment '角色ID',
    menu_id   bigint(20) not null comment '菜单ID',
    primary key(role_id, menu_id)
) engine=innodb comment = '角色和菜单关联表';
```

PostgreSQL — `script/sql/postgres/postgres_ry_vue.sql:504-509`:

```sql
create table if not exists sys_role_menu
(
    role_id int8 not null,
    menu_id int8 not null,
    constraint sys_role_menu_pk primary key (role_id, menu_id)
);
```

Oracle — `script/sql/oracle/oracle_ry_vue.sql:507-512`:

```sql
create table sys_role_menu (
  role_id  number(20)  not null,
  menu_id  number(20)  not null
);
alter table sys_role_menu add constraint pk_sys_role_menu primary key (role_id, menu_id);
```

SQL Server — `script/sql/sqlserver/sqlserver_ry_vue.sql:2283-2292`:

```sql
CREATE TABLE sys_role_menu
(
    role_id bigint NOT NULL,
    menu_id bigint NOT NULL,
    CONSTRAINT PK__sys_role__A2C36A6187BA4B17 PRIMARY KEY CLUSTERED (role_id, menu_id) ...
)
```

**Key facts**
- Exactly two columns: `role_id`, `menu_id`, both `NOT NULL`. **No surrogate id, no
  created/updated/tenant columns.**
- The only uniqueness constraint is the **composite primary key `(role_id, menu_id)`**. There is
  **no separate unique index named `uk_roleid_menuid`** in any dialect (that name comes from
  classic RuoYi; this codebase uses the composite PK).
- Constraint names: unnamed in MySQL, `sys_role_menu_pk` (PG), `pk_sys_role_menu` (Oracle),
  auto-named `PK__sys_role__…` (SQL Server).
- No index on `menu_id` alone in any dialect. The PK leads on `role_id`, so `role_id` lookups are
  indexed; `menu_id` lookups (e.g. `checkMenuExistRole`) are not indexed in MySQL/PG. (Contrast:
  `sys_user_role` in MySQL has an extra `key idx_sys_user_role_rid (role_id)` at
  `ry_vue.sql:353` — `sys_role_menu` has no such extra index.)

## 2. Role service: menu-link write path

`ruoyi-modules/ruoyi-system/src/main/java/org/dromara/system/service/impl/SysRoleServiceImpl.java`
(implements `ISysRoleService` and the cross-module `org.dromara.system.api.RoleService`).
Injected mappers: `SysRoleMapper`, `SysRoleMenuMapper`, `SysUserRoleMapper`, `SysRoleDeptMapper`.

### 2.1 Create — `insertRole(SysRoleBo)` (lines 300-308)

```java
@Override
@Transactional(rollbackFor = Exception.class)
public int insertRole(SysRoleBo bo) {
    SysRole role = MapstructUtils.convert(bo, SysRole.class);
    // 新增角色信息
    roleMapper.insert(role);
    bo.setRoleId(role.getRoleId());
    return insertRoleMenu(bo);
}
```

- **One `@Transactional`** wraps role-row insert **and** menu-link insert.
- Role id is generated by the app (snowflake) during `roleMapper.insert`; it is copied back onto
  the BO so the link insert can use it.
- `menuIds` is optional: if the BO carries an empty/null array, no links are inserted and the
  method still succeeds (returns 1).

### 2.2 Update — split into two endpoints/services

- `updateRoleBaseInfo(SysRoleBo)` (lines 316-326), `@Transactional` — **only** updates the
  `sys_role` row base fields (`roleMapper.updateById(role)`). Comment: "仅更新角色基础字段，避免影响权限分配"
  (only updates base fields, to avoid affecting permission assignment). **Does not touch
  `sys_role_menu`.** Also refuses to disable a role that still has users
  (`countUserRoleByRoleId > 0`).
- `updateRolePermission(SysRoleBo)` (lines 334-347) — the **menu + data-scope authz write**:

```java
@CacheEvict(cacheNames = CacheNames.SYS_ROLE_CUSTOM, key = "#bo.roleId")
@Override
@Transactional(rollbackFor = Exception.class)
public int updateRolePermission(SysRoleBo bo) {
    SysRole role = MapstructUtils.convert(bo, SysRole.class);
    // 更新权限相关配置字段（数据范围、树联动）。
    roleMapper.updateById(role);
    // 先清理旧菜单权限，再重建。
    roleMenuMapper.lambda().eq(SysRoleMenu::getRoleId, role.getRoleId()).delete();
    insertRoleMenu(bo);
    // 先清理旧数据权限，再按当前配置重建。
    roleDeptMapper.lambda().eq(SysRoleDept::getRoleId, role.getRoleId()).delete();
    return insertRoleDept(bo);
}
```

**This is the canonical delete-then-insert pattern**, and it is one transaction:
1. `UPDATE sys_role` (rewrites `data_scope`, `menu_check_strictly`, `dept_check_strictly`, plus any
   other non-null fields sent — `updateById` updates non-null columns only),
2. `DELETE FROM sys_role_menu WHERE role_id = ?`,
3. batch-`INSERT` the new `sys_role_menu` rows,
4. `DELETE FROM sys_role_dept WHERE role_id = ?`,
5. batch-`INSERT` the new `sys_role_dept` rows.

Because steps 2–5 share the method's `@Transactional`, a failure in any insert rolls back the
delete and the role-row update. Semantics to port: **the endpoint replaces the full menu set —
the client must send the complete desired list; an absent/empty `menuIds` clears all links.**

### 2.3 Link insert helper — `insertRoleMenu(SysRoleBo)` (lines 373-387)

```java
private int insertRoleMenu(SysRoleBo role) {
    int rows = 1;
    // 新增用户与角色管理
    List<SysRoleMenu> list = new ArrayList<>();
    for (Long menuId : role.getMenuIds()) {
        SysRoleMenu rm = new SysRoleMenu();
        rm.setRoleId(role.getRoleId());
        rm.setMenuId(menuId);
        list.add(rm);
    }
    if (CollUtil.isNotEmpty(list)) {
        rows = roleMenuMapper.insertBatch(list) ? list.size() : 0;
    }
    return rows;
}
```

- Inserts **exactly** the ids from `bo.getMenuIds()` — **no parent auto-append, no filtering
  against `sys_menu`** (see §4).
- Batch insert via MyBatis-Plus `Db.saveBatch` (`BaseMapperPlus.insertBatch`,
  `ruoyi-common/ruoyi-common-mybatis/.../BaseMapperPlus.java:121-123`), i.e. a single multi-row
  `INSERT` (chunked). `menuIds` is `Long[]` on the BO.
- Return value: number of inserted rows, or `1` when there was nothing to insert (so callers can
  treat it as success).

### 2.4 Delete — `deleteRoleById` (416-425) and `deleteRoleByIds` (433-450)

```java
@CacheEvict(cacheNames = CacheNames.SYS_ROLE_CUSTOM, key = "#roleId")
@Override
@Transactional(rollbackFor = Exception.class)
public int deleteRoleById(Long roleId) {
    // 删除角色与菜单关联
    roleMenuMapper.lambda().eq(SysRoleMenu::getRoleId, roleId).delete();
    // 删除角色与部门关联
    roleDeptMapper.lambda().eq(SysRoleDept::getRoleId, roleId).delete();
    return roleMapper.deleteById(roleId);
}
```

`deleteRoleByIds` does the same with `IN (roleIds)` for the two link tables, plus
`checkRoleDataScope(roleIds)`, per-role `checkRoleAllowed`, and refuses roles still assigned to
users. Note: `SysRole.delFlag` is `@TableLogic`, so the `sys_role` row delete is **logical**
(soft delete, `del_flag='1'`), while the `sys_role_menu` / `sys_role_dept` link deletes are
**physical** `DELETE`s.

### 2.5 Methods the task prompt guessed that do **not** exist here

- No `selectRoleMenuIdsByRoleId` on the role service — checked-keys are read via

- No `checkRoleMenu` / no validation of submitted menu ids anywhere in the write path.

## 4. Parent/child menu consistency on save

**The backend does NOT auto-append parent ids and does NOT filter the submitted ids.**
`insertRoleMenu` stores `bo.menuIds` verbatim (§2.3). There is no code anywhere in the
`ruoyi-modules` sources that appends parents on write (grep for parent-append logic finds only
the read-side filter below; the identical pattern also exists for depts in
`SysDeptMapper.selectDeptListByRoleId`).

All parent/child handling is on the **read side**, in
`SysMenuMapper.selectMenuListByRoleId(roleId, menuCheckStrictly)`
(`.../mapper/SysMenuMapper.java:117-133`):

```java
default List<Long> selectMenuListByRoleId(Long roleId, boolean menuCheckStrictly) {
    List<SysMenu> menus = this.selectJoinList(SysMenu.class, QueryBuilder.lambdaJoin("m", SysMenu.class)
        .distinct()
        .select(SysMenu::getMenuId, SysMenu::getParentId, SysMenu::getOrderNum)
        .leftJoin(SysRoleMenu.class, "srm", SysRoleMenu::getMenuId, SysMenu::getMenuId)
        .leftJoin(SysRole.class, "sr", SysRole::getRoleId, SysRoleMenu::getRoleId)
        .eq("srm", SysRoleMenu::getRoleId, roleId)
        .eq("sr", SysRole::getStatus, SystemConstants.NORMAL)   // NORMAL = "0"
        .orderByAsc("m", SysMenu::getParentId)
        .orderByAsc("m", SysMenu::getOrderNum)
        .build());
    Set<Long> parentIds = menuCheckStrictly ? new HashSet<>(StreamUtils.toList(menus, SysMenu::getParentId)) : Collections.emptySet();
    return menus.stream()
        .map(SysMenu::getMenuId)
        .filter(menuId -> !parentIds.contains(menuId))
        .toList();
}
```

Exact semantics of `checkedKeys`:
- Query: `SELECT DISTINCT m.menu_id, m.parent_id, m.order_num FROM sys_menu m
  LEFT JOIN sys_role_menu srm ON srm.menu_id = m.menu_id
  LEFT JOIN sys_role sr ON sr.role_id = srm.role_id
  WHERE srm.role_id = ? AND sr.status = '0'` (inner-join effect from the `WHERE`), ordered by
  `parent_id, order_num`. (Dead-row caveat: `distinct` + left join to `sr` with a `sr.status`
  predicate — effectively inner.)
- If `menuCheckStrictly == true`: compute the set of `parent_id`s among the stored menus and
  **drop from the result any menu_id that is itself a parent of another stored menu** — i.e.
  parents that are only half-checked in the UI are not returned as checked.
- If `menuCheckStrictly == false`: `parentIds` is empty, so **all stored ids are returned
  unchanged** (parents included).

Caller: `SysMenuServiceImpl.selectMenuListByRoleId(Long)` (lines 150-153) loads the role row and
passes `role.getMenuCheckStrictly()`.

What this means for the UI contract (frontend not in this checkout; this is the RuoYi lineage
behavior the backend is built around):
- `menu_check_strictly`/`dept_check_strictly` = "菜单树选择项是否关联显示" — whether the el-tree
  is in **check-strictly** mode (parent/child independent). Default `1` in DDL
  (`ry_vue.sql:157`); BO comment in `SysRole.java:50`: `0：父子不互相关联显示 1：父子互相关联显示`.
- Non-strict mode: checking a child auto-checks ancestors, so the client's `getCheckedKeys()`
  already contains parents; the client sends those, and the server stores them (including parent
  rows). The read-side filter is off, so all stored ids come back.
- Strict mode: the client merges checked **and** half-checked keys
  (`getCheckedKeys() + getHalfCheckedKeys()` in the classic RuoYi-Vue implementation, which the
  Vue3 `plus-ui` frontend follows) and sends that union as `menuIds`; the read side then strips
  half-checked parent ids so they render as indeterminate, not fully checked.
- Either way, **the stored rows are exactly what the client sent** — no server-side tree
  computation, no existence check against `sys_menu`.

## 5. Downstream use of the role↔menu link

Menu ids are stored **per role** (`sys_role_menu`), never per user. Users are linked to roles via
`sys_user_role` (PK `(user_id, role_id)`, plus `idx_sys_user_role_rid(role_id)` in MySQL), and
permissions are derived by joins at query time.

### 5.1 Menu list per role (checked keys for the edit form)
`SysMenuMapper.selectMenuListByRoleId` — §4. (Read side only; also used to render the role's
assigned menus.)

### 5.2 Menu list per user
`SysMenuMapper.selectMenuListByUserId(SysMenuBo, Long)` (lines 142-159) — same join but through
`sys_user_role` instead of a fixed role id, with filters on name/visible/status/type/parent:

```java
default List<SysMenuVo> selectMenuListByUserId(SysMenuBo menu, Long userId) {
    return this.selectJoinList(SysMenuVo.class, QueryBuilder.lambdaJoin("m", SysMenu.class)
        .distinct()
        .selectAll(SysMenu.class)
        .leftJoin(SysRoleMenu.class, "srm", SysRoleMenu::getMenuId, SysMenu::getMenuId)
        .leftJoin(SysUserRole.class, "sur", SysUserRole::getRoleId, SysRoleMenu::getRoleId)
        .leftJoin(SysRole.class, "sr", SysRole::getRoleId, SysRoleMenu::getRoleId)
        .eq("sur", SysUserRole::getUserId, userId)
        .eq("sr", SysRole::getStatus, SystemConstants.NORMAL)
        ... .build());
}
```

(`selectMenuTreeByUserId` at lines 167-181 is the same join restricted to `menu_type IN ('M','C')`
and `status='0'`, used to build the router tree.) Superadmin bypasses all joins:
`SysMenuServiceImpl.selectMenuList` / `selectMenuTreeByUserId` short-circuit to "all menus" when
`LoginHelper.isSuperAdmin(userId)`.

### 5.3 Permission strings (perms) per role and per user

- `SysMenuMapper.selectMenuPermsByRoleId(roleId)` (lines 53-64): `SELECT DISTINCT m.perms` via the
  same `sys_menu ← sys_role_menu ← sys_role` join, `WHERE srm.role_id = ? AND sr.status = '0' AND
  m.perms IS NOT NULL`, blank perms filtered in Java. Returns `Set<String>`.
- `SysMenuMapper.selectMenuPermsByRoleIds(Collection<Long>)` (lines 72-94): same for many roles at
  once → `Map<roleId, Set<String>>` (used for the data-scope role map, see §5.4).
- `SysMenuMapper.selectMenuPermsByUserId(userId)` (lines 33-45): same join but via
  `sys_user_role` (`sur.user_id = ?`), `sr.status='0'`, non-null perms.

### 5.4 Auth assembly at login — user → role → menu → perms

Login builds a `LoginUser` snapshot (Sa-Token session object,
`ruoyi-api/.../model/LoginUser.java` — fields `menuPermission: Set<String>`,
`rolePermission: Set<String>`, `roles: List<RoleDTO>`, `dataScopeRoleMap`).

`ruoyi-admin/src/main/java/org/dromara/web/service/SysLoginService.java:155-182`
`buildLoginUser(SysUserVo)` runs four parallel tasks:

```java

loginUser.setRolePermission(permissionService.getRolePermission(userId));  // role keys
loginUser.setRoles(roleDtos);                                              // role objects
loginUser.setDataScopeRoleMap(permissionService.getDataScopeRoleMap(roleDtos));
```

`SysPermissionServiceImpl` (`ruoyi-modules/ruoyi-system/.../service/impl/SysPermissionServiceImpl.java`):

```java
public Set<String> getRolePermission(Long userId) {
    Set<String> roles = new HashSet<>();
    if (LoginHelper.isSuperAdmin(userId)) {
        roles.add(SystemConstants.SUPER_ADMIN_ROLE_KEY);      // "superadmin"
    } else {
        roles.addAll(roleService.selectRolePermissionByUserId(userId));  // role_key strings of user's roles
    }
    return roles;
}

public Set<String> getMenuPermission(Long userId) {
    Set<String> perms = new HashSet<>();
    if (LoginHelper.isSuperAdmin(userId)) {
        perms.add("*:*:*");                                  // superadmin wildcard
    } else {
        perms.addAll(menuService.selectMenuPermsByUserId(userId));
    }
    return perms;
}
```

- `selectRolePermissionByUserId` (`SysRoleServiceImpl:136-145`) reads `role_key` of the user's
  roles from `sys_user_role` (no status filter), splits each key on `,` and unions them.
- `getDataScopeRoleMap` (`SysPermissionServiceImpl:72-85`) calls
  `menuService.selectMenuPermsByRoleIds(roleIds)` and builds
  `Map<permString, List<roleId>>` — used by the data-scope SQL interceptor to decide which roles
  apply to a row-filtering rule.
- The frontend reads them at `GET /system/user/getInfo`
  (`SysUserController.java:121-134`): `permissions = loginUser.getMenuPermission()`,
  `roles = loginUser.getRolePermission()`.
- Runtime checks (`@SaCheckPermission`) are evaluated by Sa-Token against the `LoginUser` stored
  in the session — **menu perms are not re-queried per request**; they are a login-time snapshot.
  Note the superadmin bypass constants: `SystemConstants.SUPER_ADMIN_ROLE_ID = 1761300000000000001L`,
  `SUPER_ADMIN_ROLE_KEY = "superadmin"`, `NORMAL = "0"`, `DISABLE = "1"`, `TYPE_DIR="M"`,
  `TYPE_MENU="C"`, `TYPE_BUTTON="F"` (`ruoyi-common/ruoyi-common-core/.../SystemConstants.java`).

## 6. Data-scope (数据权限) fields and endpoint separation

- `sys_role` columns: `data_scope char(1) default '1'` and `dept_check_strictly`; the custom dept
  set lives in `sys_role_dept (role_id, dept_id)` (same composite-PK shape as `sys_role_menu`).
  `data_scope` values (from `ry_vue.sql:156`): `1` all data, `2` custom (自定, uses `sys_role_dept`),
  `3` own dept, `4` own dept and below, `5` only self, `6` dept-and-below or self.
- **Menu authz and data-scope authz are NOT separate endpoints in this codebase.** The single
  `PUT /system/role/permission` handler (`editPermission`) writes `sys_role` permission fields,
  `sys_role_menu`, and `sys_role_dept` all at once via `updateRolePermission` (§2.2). The read
  side does have two endpoints: `/system/menu/roleMenuTreeselect/{roleId}` (menus) and
  `/system/role/deptTree/{roleId}` (depts), and the edit dialog submits both lists in one body.
- Data-scope dept ids are consumed at runtime by `SysDataScopeServiceImpl.getRoleCustom(roleId)`
  (`.../service/impl/SysDataScopeServiceImpl.java:40-54`) which returns the role's dept ids as a
  comma-joined string (or `"-1"` when unset) for the data-permission SQL interceptor.

## 7. Caching and invalidation

Two distinct mechanisms — one Spring cache, one session-kick:

1. **`CacheNames.SYS_ROLE_CUSTOM = "sys_role_custom#30d"`** (Redis, TTL 30 d;
   `ruoyi-common/ruoyi-common-core/.../CacheNames.java:67`). Caches **data-scope dept ids per
   role** (`SysDataScopeServiceImpl.getRoleCustom` is `@Cacheable(key = "#roleId")`). Evicted by
   `@CacheEvict` on:
   - `updateRolePermission` — key `#bo.roleId` (menu+dept rewrite, §2.2),
   - `deleteRoleById` — key `#roleId`,
   - `deleteRoleByIds` — `allEntries = true`.
   Also `CacheNames.SYS_DEPT_AND_CHILD = "sys_dept_and_child#30d"` for dept-and-children
   expansion (`CacheNames.java:72`).
   **Menu perms are NOT in this cache.**
2. **Online-user session kick** (the actual invalidation for menu/role permissions): on any of
   `edit` / `editPermission` / `changeStatus` success, `SysRoleController` publishes
   `OnlineUserCleanEvent.byRole(roleId)`; on user-role grant/revoke,
   `SysRoleServiceImpl` publishes `OnlineUserCleanEvent.byUsers(userIds)`. The listener
   (`.../listener/OnlineUserCleanListener.java`) is `@Async @TransactionalEventListener(AFTER_COMMIT)`
   and calls `roleService.cleanOnlineUserByRole(roleId)` /
   `cleanOnlineUser(userIds)` (`SysRoleServiceImpl:536-600`), which scans Sa-Token tokens
   (`StpUtil.searchTokenValue`) and **logs out** sessions whose `LoginUser.roles` contain the
   role (resp. whose userId matches). Affected users must re-login, which rebuilds
   `menuPermission`/`rolePermission`/`roles` from the DB — i.e. invalidation by forced re-login,
   not by evicting a permission cache.

## 8. Minimal semantic checklist for the Go/ent port

1. Table: two-column join entity `(role_id, menu_id)`, composite unique/PK on both; no surrogate
   key; add an index on `menu_id` if you run `checkMenuExistRole`-style deletes/queries.
2. Role create = one transaction: insert `sys_role`, then batch-insert `sys_role_menu` from the
   submitted `menuIds` (empty list ⇒ no rows, still success).
3. Role base-info update does **not** touch `sys_role_menu`.
4. Menu+data-scope authz = one transaction: update `sys_role` permission fields →
   delete `sys_role_menu` by role_id → batch insert new rows → delete `sys_role_dept` by role_id →
   batch insert new dept rows. Replace semantics: client sends the full set; empty set clears.
5. No server-side parent-id auto-append and no validation of menu ids on write — store verbatim.
6. Read side (`checkedKeys` for the edit form) returns stored menu ids, minus any id that is the
   parent of another stored id **only when `menu_check_strictly` is true**; otherwise all ids.
7. Permission resolution is join-based per user at login: `sys_user_role → sys_role (status='0') →
   sys_role_menu → sys_menu (perms not null)`; superadmin bypasses with `*:*:*` / `"superadmin"`.
8. Invalidation: clear the per-role data-scope cache on permission write/role delete; kick online
   sessions of affected roles/users after the write commits (re-login rebuilds the permission
   snapshot). If you instead serve perms from a cache, the eviction scope must cover the same
   events.
