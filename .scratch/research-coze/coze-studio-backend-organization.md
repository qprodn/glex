# Coze Studio Go 后端的业务代码组织方式

调研目标：回答 Coze Studio 如何组织领域对象、Repository 接口、业务逻辑、持久化实现、DTO、Handler 与依赖注入，并判断其做法对 glex `internal/biz` 的参考价值。

调研范围仅使用 `coze-dev/coze-studio` 官方仓库及官方 Wiki。源码快照为 `main` 分支提交 [`fefb05ff`](https://github.com/coze-dev/coze-studio/tree/fefb05ff27be1da939612fbf9faf5db62583b8ae)（2026-07-29）。

## 结论先行

Coze 的答案不是“一个文件同时放 DO、Repo、Usecase”，而是：

1. 先按业务域纵向分包，例如 `conversation`、`knowledge`、`workflow`。
2. 在域内再按 `entity`、`repository`、`service`、`internal/dal` 等职责拆包或拆文件。
3. HTTP/Thrift DTO 与 Handler 位于 `api`，跨领域用例编排和 DTO 转换位于 `application`。
4. 复杂度不同的领域采用不同粒度，没有强制所有领域使用完全相同的文件模板。

因此，Coze 明显偏向“**领域内按职责拆开，并随复杂度继续加深结构**”，不是建立全局 `BO/`、`VO/` 对象仓库。它的 `workflow/entity/vo` 也不能直接理解为传统后台里的 Response View Object；其中混有策略、命令参数、元数据和直接包装 API 生成类型的结构。

Coze 官方把后端概括为 DDD：`api` 处理接口，`application` 组合领域对象与基础设施，`domain` 承载核心业务逻辑，`infra` 提供基础设施，并另设 `crossdomain` 作为跨域层。[官方开发规范](https://github.com/coze-dev/coze-studio/wiki/7.-Development-Standards) 与仓库内的 [CLAUDE.md](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/CLAUDE.md#L86-L106) 都给出了这一定位。

但源码并非教科书式严格分层：部分领域服务会直接引用 API 类型、请求上下文工具、GORM 或 `infra` 接口；领域仓储实现也经常放在 `domain/<域>/internal/dal`，而不是统一放到顶层 `infra`。所以应以实际依赖为准，不能只根据目录名称判断边界。

## 总体结构

官方目录与实际源码可归纳为：

```text
backend/
├── api/
│   ├── model/                 # Thrift 生成的请求/响应 DTO
│   ├── handler/coze/          # Hertz Handler：绑定、校验、调用 application
│   └── router/                # 生成的路由
├── application/<domain>/      # 用例编排、权限检查、DTO ↔ 领域模型转换
├── domain/<domain>/
│   ├── entity/                # 领域实体及领域内部参数；部分类型是别名/包装
│   ├── repository/            # Repository 接口及创建函数（部分域采用此结构）
│   ├── service/               # 领域服务接口与实现
│   └── internal/dal/          # GORM PO、Query 和 Repository 实现
├── crossdomain/<domain>/      # 跨域契约、模型、适配实现和默认服务注册
├── infra/                     # ID、缓存、对象存储、搜索、事件总线等共享技术能力
└── application/application.go # 手工组装所有服务
```

DTO 是从 Thrift IDL 生成的。例如 Conversation 的接口契约在 [`idl/conversation/conversation.thrift`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/idl/conversation/conversation.thrift)，生成后的 Go DTO 明确标记为 `Code generated by thriftgo`，位于 [`backend/api/model/conversation/conversation/conversation.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/api/model/conversation/conversation/conversation.go#L15-L24)。

## 具体案例：Conversation

Conversation 是观察“一个普通资源如何落地”的最清晰样本。一次请求的主要路径是：

```text
Thrift DTO
  → Hertz Handler
  → ConversationApplicationService
  → Conversation domain service
  → ConversationRepo interface
  → internal/dal ConversationDAO
  → GORM PO / MySQL
```

### 1. Entity 单独放

[`domain/conversation/conversation/entity/conversation.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/domain/conversation/conversation/entity/conversation.go) 放 `Conversation`、`CreateMeta`、`ListMeta`、`UpdateMeta` 等领域侧对象，没有放领域服务实现。

这里的 `Conversation` 实际是 `crossdomain/conversation/model.Conversation` 的类型别名，而且 `CreateMeta`、`ListMeta` 使用了生成 API 包中的 `common.Scene`。这说明 Coze 的 entity 并非像 glex 约定那样完全独立于 DTO/跨域模型。

### 2. Repository 接口单独放

[`domain/conversation/conversation/repository/repository.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/domain/conversation/conversation/repository/repository.go) 同时包含：

- `ConversationRepo` 接口；
- `NewConversationRepo(db, idGen)` 创建函数；
- 对内部 DAL 实现 `dal.NewConversationDAO` 的调用。

创建函数返回接口，这一点和 glex 的 `New<Resource>Repo(...) biz.<Resource>Repo` 约定相似；区别是 Coze 的创建函数和实现入口仍位于 domain 树下，并且构造函数直接接收 GORM DB。

### 3. 领域服务接口与实现分文件

[`service/conversation.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/domain/conversation/conversation/service/conversation.go) 只声明 `Conversation` 领域服务接口；[`service/conversation_impl.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/domain/conversation/conversation/service/conversation_impl.go) 则定义 `Components`、构造函数和实际方法。

其简单 CRUD 方法主要负责构造实体并调用 Repo。这说明“某文件只放接口或对象”在 Coze 中是正常且有意的组织方式；文件/包按职责命名，不要求每个资源文件都同时具备 Entity、Repo 和 Service。

### 4. 持久化实现隐藏在 domain 的 internal 下

[`internal/dal/dao.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/domain/conversation/conversation/internal/dal/dao.go) 实现 Repo，持有 `*gorm.DB` 和生成 Query，并在 `conversationDO2PO` / `conversationPO2DO` 中转换持久化模型。GORM 生成 PO 位于同一 `internal/dal/model` 下。

`internal` 使外部包不能直接依赖 DAL，但这仍不同于 glex 的顶层 `internal/data`：Coze 采用“持久化实现跟随领域”的垂直切分，glex 采用“data 层统一实现 biz 接口”的分层切分。

### 5. Application 层承担用例编排和 DTO 转换

[`application/conversation/conversation.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/application/conversation/conversation.go) 直接接收生成的 API Request，读取身份上下文、做权限/归属检查、调用多个领域服务，并将领域对象转换成 API Response。

例如 `CreateConversation` 把 `CreateConversationRequest` 转成 `entity.CreateMeta`，再把返回实体转成 `ConversationData`；`ClearHistory` 会组合查询、校验、删除和重新创建。由此可见：

- 单资源规则可位于 domain service；
- 横跨多个领域服务、权限和传输模型的流程位于 application；
- Handler 不承载这些业务编排。

### 6. Handler 很薄

生成的 [`api/handler/coze/conversation_service.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/api/handler/coze/conversation_service.go) 主要执行绑定/校验、调用全局 `application.ConversationSVC`、映射 HTTP 错误并返回 JSON。这与 glex 的 service 边界职责相近，但 Coze 将真正的 DTO 转换和较多鉴权逻辑下沉到了 application。

### 7. 使用手工依赖注入，而不是 Wire

[`application/conversation/init.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/application/conversation/init.go) 手工创建 Message Repo/Service、Conversation Repo/Service、AgentRun Repo/Service，再写入包级全局服务变量。

总入口 [`application/application.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/application/application.go#L117-L171) 又按 basic、primary、complex 三个依赖层级初始化应用服务，并通过 `crossdomain.SetDefaultSVC(...)` 注册跨域默认实现。

这种方式能显式控制大型依赖图的初始化顺序，但全局服务和默认注册表增加了隐藏依赖及测试隔离成本。glex 已经有 Wire，不需要照搬这部分。

## 不同领域并不使用完全相同的模板

### User：相对普通的领域也采用职责拆包

User 虽然比 Workflow 简单，仍分别设置 `entity`、`repository`、`service` 和 `internal/dal`：[`entity/user.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/domain/user/entity/user.go) 定义用户实体，[`service/user.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/domain/user/service/user.go) 放服务接口和领域请求形态，[`service/user_impl.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/domain/user/service/user_impl.go) 放业务实现。

这说明 Coze 的默认倾向确实比 Kratos Layout 更偏“职责分离”，而不是简单资源共置。不过 [`repository/repository.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/domain/user/repository/repository.go) 直接收发 `internal/dal/model.User`，同样存在 PO 穿过 Repo 契约的边界折中。

### Knowledge：对象、仓储和逻辑进一步拆开，但边界较松

Knowledge 域把实体拆到多个文件，把四个 Repo 接口集中在 [`repository/repository.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/domain/knowledge/repository/repository.go)，把领域服务接口及大量内部 Request/Response 放在 [`service/interface.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/domain/knowledge/service/interface.go)，再按知识库、检索、表格、事件处理等职责拆分实现文件。[`service/knowledge.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/domain/knowledge/service/knowledge.go) 是其中的主要实现。

但它并不遵守 glex 式的纯 DO 边界：Repo 接口直接收发 `internal/dal/model` GORM PO，并暴露 `*gorm.DB` 事务；domain service 还直接依赖缓存、对象存储、搜索、事件总线等 `infra` 接口。对应证据可见 [`repository/repository.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/domain/knowledge/repository/repository.go#L22-L101) 和 [`service/knowledge.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/domain/knowledge/service/knowledge.go#L22-L113)。

这是一种为复杂 AI 基础设施编排服务的工程折中，不宜作为 glex 放宽 `biz` 层依赖规则的依据。

### Workflow：按领域能力深度拆分，并出现 `entity/vo`

Workflow 域复杂得多：根目录的 [`interface.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/domain/workflow/interface.go) 同时声明大型 `Service` 和 `Repository` 契约；`entity/` 放核心实体，`entity/vo/` 放画布、元数据、查询策略、发布参数等结构；`service/` 放实现；`internal/repo/`、`internal/compose/`、`internal/execute/` 和 `internal/nodes/` 分别承载持久化、编排执行与节点机制。[领域目录](https://github.com/coze-dev/coze-studio/tree/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/domain/workflow)

这里的 `vo` 并非单一含义：例如 [`entity/vo/workflow_info.go`](https://github.com/coze-dev/coze-studio/blob/fefb05ff27be1da939612fbf9faf5db62583b8ae/backend/domain/workflow/entity/vo/workflow_info.go) 直接包装生成的 API Workflow 类型并自定义 JSON，而其他 `vo` 文件又包含 `Meta`、Policy、Canvas、校验信息等领域内部结构。因此不能因为 Coze 有 `vo/`，就推导出 glex 应建立统一 BO/VO 目录。

Workflow 也展示了“复杂度驱动拆分”：它先形成了清晰且庞大的领域边界，才在域内建立更多子包；这不是对普通 CRUD 资源的默认模板。

## Coze 实际采用的组织原则

| 问题 | Coze 的选择 | 主要收益 | 主要代价 |
|---|---|---|---|
| 顶层如何拆 | 按 conversation、knowledge、workflow 等业务域纵切 | 一个复杂业务域的代码集中 | 域内仍可能很大 |
| 域内如何拆 | entity / repository / service / internal | 契约、实现、模型易定位 | 修改简单功能时跨文件较多 |
| DTO 放哪 | IDL + api/model 生成 | API-first、契约统一 | 某些 domain 仍反向引用 API 类型 |
| 用例编排放哪 | application/<domain> | 适合跨服务流程与 DTO 转换 | application 可能变成大服务 |
| Repo 实现放哪 | 多数随领域放入 internal/dal | 强垂直内聚、实现不可外部引用 | domain 树内混入 GORM/存储细节 |
| 依赖注入 | application 中手工组装 + 全局默认服务 | 初始化顺序显式 | 全局状态、隐藏依赖、测试隔离更难 |
| 文件模板 | 各域按复杂度选择 | 避免简单域过度抽象 | 全仓一致性较弱 |

## 对 glex 的具体启示

### 值得借鉴

1. **复杂流程可以拆文件。** `auth.go`、`login_session.go`、`online_session.go` 分开是正常的；不必为了视觉一致，把 DO、接口和逻辑塞回一个文件。
2. **按业务概念拆，不按对象后缀拆。** 登录、授权快照、会话、失败计数分别形成主题，比全局 `bo/`、`vo/` 更容易维护。
3. **共享对象和契约可以单独放。** 当 `LoginSession` 与 `LoginSessionRepo` 被登录、在线会话、鉴权和安全变更共同使用时，单独文件具有合理的依赖中心价值。
4. **复杂度达到阈值后再拆包。** 如果 auth 将来成为真正独立且庞大的领域，可以参考 Coze 的 `domain/conversation/...` 纵向域结构；当前只拆同一个 `package biz` 下的文件更轻量。

### 不应照搬

1. 不要因为 Coze 有 `entity/vo` 就给 glex 建通用 `BO/VO` 目录；Coze 的 `vo` 语义本身就不统一。
2. 不要把 Repo 实现、GORM PO 或存储客户端搬进 `biz`。glex 的 `biz → Repo interface ← data` 边界更严格，也更适合当前 Kratos 模板。
3. 不要让 `biz` 接受 proto DTO 或返回展示模型。Coze 源码存在这种依赖，但这与 glex 已明确的 DTO ↔ DO ↔ PO 契约冲突。
4. 不需要用全局 `XXXService` 或 `SetDefaultSVC` 替代 Wire；glex 的组合根已经更清晰、可测试。

## 对当前问题的建议

针对 `internal/biz/login_session.go`，Coze 的经验更支持“**保留独立文件，但继续处在同一个 biz 包**”：

```text
internal/biz/
├── auth.go                 # 认证用例编排
├── auth_login.go           # 登录所需契约/参数（如确有需要）
├── login_session.go        # LoginSession + LoginSessionRepo
├── online_session.go       # 在线会话管理用例
└── security_change.go      # 安全变化后的会话撤销规则
```

简单资源仍可保持 `DO + Repo + Usecase` 共置；复杂流程允许按主题拆文件。等 auth 的领域边界、依赖方向和代码规模都足够稳定，再讨论 `internal/biz/auth/` 子包。

一句话总结：**Coze 不是用统一文件模板获得一致性，而是用领域边界获得一致性；域内文件是否只放接口、只放实体或同时放逻辑，由该领域的复杂度决定。**

## 专项：crossdomain 跨域防腐层怎么做的（2026-08-25 补充调研）

针对 glex 拆分 iam 的跨域契约设计，专项调研了 crossdomain 层的完整机制。快照仍为 `main` 分支。

### 包结构（16 个提供方包，形状统一）

```text
backend/crossdomain/<provider>/     # 按提供方命名：user、permission、conversation、plugin…共 16 个
├── contract.go                     # 消费方视角的最小接口 + defaultSVC 机制 + mockgen 指令
├── model/                          # 扁平 DTO 快照（标量 ID、json 标签、无方法）
├── impl/                           # InitDomainService(提供方 domain service) → 契约接口，纯透传适配器
└── <provider>mock/                 # mockgen 生成的测试替身
```

### 四个关键机制

1. **契约按消费方裁剪，不镜像提供方全量服务。** [`crossdomain/permission/contract.go`](https://github.com/coze-dev/coze-studio/blob/main/backend/crossdomain/permission/contract.go) 的 `Permission` 接口只有一个方法：`CheckAuthz(ctx, *model.CheckAuthzData) (*model.CheckAuthzResult, error)`；[`crossdomain/user/contract.go`](https://github.com/coze-dev/coze-studio/blob/main/backend/crossdomain/user/contract.go) 的 `User` 只有两个空间查询。
2. **适配器住在 crossdomain 里，不放 infra。** [`crossdomain/user/impl/user.go`](https://github.com/coze-dev/coze-studio/blob/main/backend/crossdomain/user/impl/user.go)：`InitDomainService(u service.User) crossuser.User` 返回包裹提供方 domain service 的透传结构体。契约甚至可以直接类型别名提供方 entity（`type EntitySpace = entity.Space`），或内联定义请求结构体（conversation 的 `ClearConversationHistoryReq`）。
3. **组合根分层注册默认服务。** [`application/application.go`](https://github.com/coze-dev/coze-studio/blob/main/backend/application/application.go) 按 basic/primary/complex 依赖层级调用 `cross<provider>.SetDefaultSVC(<provider>Impl.InitDomainService(<providerApp>.DomainSVC))`，每个契约包自带 `var defaultSVC` + `DefaultSVC()`/`SetDefaultSVC()`。
4. **服务定位器式消费，调用点可深入其他域的 domain 层。** 代码搜索 `DefaultSVC().` 命中 30+ 处，遍布 `domain/workflow/internal/nodes/...`、`domain/agent/singleagent/...`、`domain/knowledge/...` 等域内深处，例如 workflow 插件节点内联调用 `crossplugin.DefaultSVC().MGetOnlinePlugins(ctx, []int64{pluginID})`。域与域之间因此零直接 import——这正是 wiki 所称"跨域防腐层：定义跨域 API、实现跨域 API、防止域之间的直接依赖"。

### model/ 快照的形状

[`crossdomain/conversation/model/conversation.go`](https://github.com/coze-dev/coze-studio/blob/main/backend/crossdomain/conversation/model/conversation.go)：`Conversation` 是扁平 DTO（int64 ID、string Ext、unix 时间戳，无方法），请求类型 `GetCurrent` 也是扁平结构。可以引用 API 生成类型（`common.Scene`），也存在包内重复定义枚举的瑕疵——说明快照以"消费方够用"为准，不追求与域模型同构。

### glex 的采纳与有意偏离（ADR 0017）

采纳：`internal/crossdomain/<provider>` 固定形状（contract.go / model / impl / mock）；适配器住 crossdomain、包提供方 domain 能力；所有跨模块调用不分调用方数量一律走防腐层（取代 0016 的"单调用方留 domain 端口"规则）；契约只返回小快照。

有意偏离：**不搬 `defaultSVC` 全局服务定位器**。Coze 需要它是因为手写 DI 且调用点深入域内；glex 用 Wire、跨域调用点都在 Usecase 层，消费保留构造器注入，cmd 仍是唯一组合根，域包仍不 import crossdomain。另外 glex 禁止契约别名提供方 DO——快照必须落在 model/ 包，避免消费方反向 import 提供方 domain。
