Source: vendored backend at `RuoYi-Vue-Plus/` (Java/Spring Boot + MyBatis-Plus). Backend only — the Vue frontend (`ruoyi-vue-plus-ui`) is NOT vendored, so frontend behavior below is inferred from server contracts only.

## 1. `sys_role` table (MySQL DDL, `script/sql/ry_vue.sql` lines 151–170)

```sql
create table sys_role (
    role_id              bigint(20)      not null                   comment '角色ID',
    role_name            varchar(30)     not null                   comment '角色名称',
    role_key             varchar(100)    not null                   comment '角色权限字符串',
    role_sort            int(4)          not null                   comment '显示顺序',
    data_scope           char(1)         default '1'                comment '数据范围（1：全部 2：自定 3：本部门 4：本部门及以下 5：仅本人 6：部门及以下或本人）',
    menu_check_strictly  tinyint(1)      default 1                  comment '菜单树选择项是否关联显示',
    dept_check_strictly  tinyint(1)      default 1                  comment '部门树选择项是否关联显示',
    status               char(1)         not null                   comment '角色状态（0正常 1停用）',
    del_flag             char(1)         default '0'                comment '删除标志（0代表存在 1代表删除）',
    create_dept          bigint(20)      default null               comment '创建部门',
    create_by            bigint(20)      default null               comment '创建者',
    create_time          datetime                                   comment '创建时间',
    update_by            bigint(20)      default null               comment '更新者',
    update_time          datetime                                   comment '更新时间',
    remark               varchar(500)    default null               comment '备注',
    primary key (role_id),
    key idx_sys_role_create_dept (create_dept),
    key idx_sys_role_create_by   (create_by)
) engine=innodb comment = '角色信息表';
```

Facts:
- Column order in the row: `role_id, role_name, role_key, role_sort, data_scope, menu_check_strictly, dept_check_strictly, status, del_flag, create_dept, create_by, create_time, update_by, update_time, remark`.
- **No unique index on `role_name` / `role_key`** — uniqueness is enforced in application code only (`checkRoleNameUnique` / `checkRoleKeyUnique`).
- **Logic delete**: `del_flag` is mapped with MyBatis-Plus `@TableLogic` on the `SysRole.delFlag` field, so `deleteById`/`deleteByIds` become `UPDATE sys_role SET del_flag='1' ...`, and every auto-generated query appends `del_flag = '0'`.
- `create_by`/`update_by` are **bigint user IDs** (Plus style; classic RuoYi uses varchar login names). `create_dept` is a Plus addition.
- IDs are **snowflake IDs** (seed data: `1761300000000000001` = 超级管理员 role), generated by the ID generator, not auto-increment.
- Java mapping (`SysRole.java`): `roleId` `@TableId(value="role_id")`; `menuCheckStrictly`/`deptCheckStrictly` are `Boolean`; `status`/`delFlag`/`dataScope` are `String`; `roleSort` is `Integer`; extends `BaseEntity` (createDept/createBy/createTime/updateBy/updateTime, auto-filled via `FieldFill.INSERT` / `INSERT_UPDATE`).

Seed rows: role 1 = `超级管理员`/`superadmin`, role 3 = `本部门及以下`/`test1` (data_scope 4), role 4 = `仅本人`/`test2` (data_scope 5).

## 2. `sys_role_menu` table (lines 366–370)

```sql
create table sys_role_menu (
    role_id   bigint(20) not null comment '角色ID',
    menu_id   bigint(20) not null comment '菜单ID',
    primary key(role_id, menu_id)
) engine=innodb comment = '角色和菜单关联表';
```

Facts:
- Exactly 2 columns; composite PK `(role_id, menu_id)`; **no FK constraints**, no `del_flag`, no timestamps, no status.
- Java mapping (`SysRoleMenu.java`): `roleId` `@TableId(type = IdType.INPUT)`, `menuId` plain column.
- **Delete strategy: hard DELETE, always**. There is no logic delete on this table and no row-level deactivation. Role update = `DELETE FROM sys_role_menu WHERE role_id = ?` then re-INSERT of the full submitted set.

## 3. REST endpoints involved in role ↔ menu association

Base controller paths: `SysRoleController @RequestMapping("/system/role")`, `SysMenuController @RequestMapping("/system/menu")`. Auth via Sa-Token `@SaCheckPermission` (perm string) and `@SaCheckRole`; super admin role key = `superadmin` (`SystemConstants.SUPER_ADMIN_ROLE_KEY`), super admin role/user ID = `1761300000000000001`.

Response envelope `R<T>`: `{"code": int, "msg": string, "data": T}` — `code 200` success, `500` error, `601` warn (`R.ok / R.fail / R.warn`). Paged list data is `PageResult`: `{"total": long, "rows": [...]}`.

## 4. Business logic

### 4.1 `insertRole` — create role with menuIds (SysRoleServiceImpl lines 300–308)

```java
@Override
@Transactional(rollbackFor = Exception.class)
public int insertRole(SysRoleBo bo) {
    SysRole role = MapstructUtils.convert(bo, SysRole.class);
    // 新增角色信息
    roleMapper.insert(role);
    bo.setRoleId(role.getRoleId());
    return insertRoleMenu(bo);
}
```
- Single DB transaction. `roleMapper.insert` = MyBatis-Plus INSERT (snowflake `role_id`, auto-fill `create_dept/create_by/create_time/update_by/update_time`).
- Then `insertRoleMenu`:

```java
private int insertRoleMenu(SysRoleBo role) {
    int rows = 1;
    // 新增用户与角色管理
    List<SysRoleMenu> list = new ArrayList<>();
    for (Long menuId : role.getMenuIds()) {
        SysRoleMenu rm = new SysRoleMenu();
        rm.setRoleId(role.getRoleId());
        rm.setMenuId(menuId);
        list.add(rm);
    }
    if (CollUtil.isNotEmpty(list)) {
        rows = roleMenuMapper.insertBatch(list) ? list.size() : 0;
    }
    return rows;
}
```
- **No null guard on `role.getMenuIds()` in this vendored copy** — a request without `menuIds` NPEs here. No dedupe (PK would reject dupes), no existence check of menu ids, **no menuCheckStrictly server-side expansion — exactly the submitted menuIds are stored**.
- `insertBatch` = MyBatis-Plus `Db.saveBatch` (batch insert).
- Returns `list.size()` (or 1 when empty); controller `toAjax(rows>0)`.

### 4.2 `updateRoleBaseInfo` — `PUT /system/role` (lines 316–326)

```java
@Override
@Transactional(rollbackFor = Exception.class)
public int updateRoleBaseInfo(SysRoleBo bo) {
    SysRole role = MapstructUtils.convert(bo, SysRole.class);
    if (SystemConstants.DISABLE.equals(role.getStatus()) && this.countUserRoleByRoleId(role.getRoleId()) > 0) {
        throw new ServiceException("角色已分配，不能禁用!");
    }
    // 仅更新角色基础字段，避免影响权限分配。
    return roleMapper.updateById(role);
}
```
- Just `updateById` (updates all non-null columns). **No sys_role_menu / sys_role_dept writes** — `menuIds`/`deptIds` in the body are ignored.
- Controller publishes `OnlineUserCleanEvent.byRole(roleId)` on success (kicks online users holding the role).

### 4.3 `updateRolePermission` — `PUT /system/role/permission` (lines 334–347) — **the menu write path**

```java
@CacheEvict(cacheNames = CacheNames.SYS_ROLE_CUSTOM, key = "#bo.roleId")
@Override
@Transactional(rollbackFor = Exception.class)
public int updateRolePermission(SysRoleBo bo) {
    SysRole role = MapstructUtils.convert(bo, SysRole.class);
    // 更新权限相关配置字段（数据范围、树联动）。
    roleMapper.updateById(role);
    // 先清理旧菜单权限，再重建。
    roleMenuMapper.lambda().eq(SysRoleMenu::getRoleId, role.getRoleId()).delete();
    insertRoleMenu(bo);
    // 先清理旧数据权限，再按当前配置重建。
    roleDeptMapper.lambda().eq(SysRoleDept::getRoleId, role.getRoleId()).delete();
    return insertRoleDept(bo);
}
```
- **Always delete-then-re-insert ALL `sys_role_menu` rows for the role** — unconditionally, regardless of `menuCheckStrictly`. The submitted `menuIds` array is the complete desired set (the frontend computes it; when parent-child are linked, checking a parent checks descendants in the tree, so the submitted list is already "expanded" client-side).
- Also rewrites `sys_role_dept` (data scope) the same way.
- `roleMapper.updateById(role)` writes `data_scope`, `menu_check_strictly`, `dept_check_strictly` plus any other non-null base fields.
- `@CacheEvict(SYS_ROLE_CUSTOM, key=roleId)` — the cached custom data-scope dept-id string is invalidated. Controller then publishes `OnlineUserCleanEvent.byRole(roleId)`.
- **`menuCheckStrictly` is therefore purely read-side/frontend**: the server does not auto-check parents, does not expand children, and does not skip parents when writing.

### 4.4 `deleteRoleById` (lines 416–425) and `deleteRoleByIds` (lines 433–450)

```java
@Override
@Transactional(rollbackFor = Exception.class)
public int deleteRoleById(Long roleId) {
    // 删除角色与菜单关联
    roleMenuMapper.lambda().eq(SysRoleMenu::getRoleId, roleId).delete();
    // 删除角色与部门关联
    roleDeptMapper.lambda().eq(SysRoleDept::getRoleId, roleId).delete();
    return roleMapper.deleteById(roleId);   // logic delete -> UPDATE del_flag='1'
}

@Override
@Transactional(rollbackFor = Exception.class)
public int deleteRoleByIds(Collection<Long> roleIds) {
    this.checkRoleDataScope(roleIds);
    List<SysRole> roles = roleMapper.selectByIds(roleIds);
    for (SysRole role : roles) {
        checkRoleAllowed(BeanUtil.toBean(role, SysRoleBo.class));
        if (countUserRoleByRoleId(role.getRoleId()) > 0) {
            throw new ServiceException(String.format("%1$s已分配，不能删除!", role.getRoleName()));
        }
    }
    // 删除角色与菜单关联
    roleMenuMapper.lambda().in(SysRoleMenu::getRoleId, roleIds).delete();
    // 删除角色与部门关联
    roleDeptMapper.lambda().in(SysRoleDept::getRoleId, roleIds).delete();
    return roleMapper.deleteByIds(roleIds);
}
```
- `sys_role_menu` cleanup is a **hard DELETE** (`DELETE FROM sys_role_menu WHERE role_id IN (...)`); the `sys_role` row itself is a **logic delete** (`del_flag='1'`) — a soft-deleted role therefore loses its menu links entirely (they are not restored on un-delete; Plus has no role restore flow).
- `deleteRoleByIds` guards: data scope check, super-admin protection, "已分配，不能删除" when `sys_user_role` rows exist.
- `deleteRoleById` (single) has **no** user-assignment or data-scope guard; it is only in the interface — the controller only exposes `deleteRoleByIds`.

### 4.5 `menuCheckStrictly` — exact server-side semantics

Server logic lives entirely in the READ path: `SysMenuServiceImpl.selectMenuListByRoleId` → `SysMenuMapper.selectMenuListByRoleId(roleId, role.getMenuCheckStrictly())`:

```java
default List<Long> selectMenuListByRoleId(Long roleId, boolean menuCheckStrictly) {
    List<SysMenu> menus = this.selectJoinList(SysMenu.class, QueryBuilder.lambdaJoin("m", SysMenu.class)
        .distinct()
        .select(SysMenu::getMenuId, SysMenu::getParentId, SysMenu::getOrderNum)
        .leftJoin(SysRoleMenu.class, "srm", SysRoleMenu::getMenuId, SysMenu::getMenuId)
        .leftJoin(SysRole.class, "sr", SysRole::getRoleId, SysRoleMenu::getRoleId)
        .eq("srm", SysRoleMenu::getRoleId, roleId)
        .eq("sr", SysRole::getStatus, SystemConstants.NORMAL)
        .orderByAsc("m", SysMenu::getParentId)
        .orderByAsc("m", SysMenu::getOrderNum)
        .build());
    Set<Long> parentIds = menuCheckStrictly ? new HashSet<>(StreamUtils.toList(menus, SysMenu::getParentId)) : Collections.emptySet();
    return menus.stream()
        .map(SysMenu::getMenuId)
        .filter(menuId -> !parentIds.contains(menuId))
        .toList();
}
```

Equivalent SQL:
```sql
SELECT DISTINCT m.menu_id, m.parent_id, m.order_num
FROM sys_menu m
LEFT JOIN sys_role_menu srm ON m.menu_id = srm.menu_id
LEFT JOIN sys_role sr     ON sr.role_id = srm.role_id
WHERE srm.role_id = #{roleId} AND sr.status = '0'   -- (+ del_flag='0' via @TableLogic)
ORDER BY m.parent_id, m.order_num
```

Semantics of the returned `checkedKeys`:
- The base set = **every menu row linked in `sys_role_menu` for the role** (no `menu_type` filter → **buttons (F) are included**; directories (M), menus (C), buttons (F) all present).
- **`menuCheckStrictly == true`** (“父子互相关联显示”): drop any menu whose `menu_id` also appears as the `parent_id` of another assigned menu (i.e., parent nodes that have children assigned are treated as indeterminate/half-checked and excluded from `checkedKeys`).
- **`menuCheckStrictly == false`**: return **all** assigned ids (parents + children + buttons) unchanged.
- Edge cases: a selected parent whose children are NOT selected stays in `checkedKeys`; the filter only removes parents-of-other-selected-menus. `role.getMenuCheckStrictly()` unboxes a `Boolean` — a NULL value in `sys_role.menu_check_strictly` would NPE (column defaults to 1, so normally non-null).
- `selectMenuListByRoleId(Long roleId)` first loads the role (`roleMapper.selectById(roleId)`) to read the flag (SysMenuServiceImpl line 150–153).

**Write side: no auto-checking.** `insertRoleMenu`/`updateRolePermission` never consult `menuCheckStrictly`; they store exactly the submitted `menuIds`. The check/uncheck linkage lives in the (unvendored) frontend element-plus tree: `check-strictly = !menuCheckStrictly`.

### 4.6 Permission set (perms) computation from role-menu

All in `SysMenuMapper` (MyBatis-Plus-Join), projecting `sys_menu.perms`:

- `selectMenuPermsByRoleId(Long roleId)`:
```sql
SELECT DISTINCT m.perms FROM sys_menu m
LEFT JOIN sys_role_menu srm ON m.menu_id = srm.menu_id
LEFT JOIN sys_role sr     ON sr.role_id = srm.role_id
WHERE srm.role_id = ? AND sr.status = '0' AND m.perms IS NOT NULL
```
Returns `Set<String>` of non-blank perms (e.g. `"system:role:list"`). **Note the `sr.status = '0'` filter: disabled roles do not contribute perms.**
- `selectMenuPermsByRoleIds(roleIds)` → `Map<Long, Set<String>>` (`SysRoleMenuPermVo {roleId, perms}` rows grouped in Java).
- `selectMenuPermsByUserId(userId)` — same joins plus `sys_user_role sur ON sur.role_id = srm.role_id WHERE sur.user_id = ? AND sr.status='0' AND m.perms IS NOT NULL` → user's perms across all their active roles.

Aggregation (`SysPermissionServiceImpl`):
- `getMenuPermission(userId)`: super admin (`userId == 1761100000000000001`) → `{"*:*:*"}`; else `selectMenuPermsByUserId`.
- `getRolePermission(userId)`: super admin → `{"superadmin"}`; else `role_key` of the user's roles (`selectRolesByUserId` joins `sys_user_role` with **no status filter** — disabled roles still contribute their `role_key` here).
- `getDataScopeRoleMap(roles)` — used by the data-permission SQL plugin: maps each perm string → list of roleIds having it (via `selectMenuPermsByRoleIds`).
- `SYS_ROLE_CUSTOM` cache (`SysDataScopeServiceImpl.getRoleCustom`) caches the comma-joined custom dept ids per role from `sys_role_dept`; evicted by `updateRolePermission` and role deletion.

### 4.7 Validation rules on role fields

- Bean validation (`SysRoleBo`): `roleName` `@NotBlank` + `@Size(max=30)`; `roleKey` `@NotBlank` + `@Size(max=100)`; `roleSort` `@NotNull`. (Only enforced on `POST /system/role` and `PUT /system/role` via `@Validated`.)
- Unique checks (application-level; no DB unique index): `checkRoleNameUnique` and `checkRoleKeyUnique` — exists-query on the field with `neIfPresent(roleId)`. Failure messages: `"新增/修改角色'X'失败，角色名称已存在"` / `"...角色权限已存在"`.
- Super-admin protection `checkRoleAllowed` (SysRoleServiceImpl lines 230–252):
  - operating on role_id `1761300000000000001` → `"不允许操作超级管理员角色"`;
  - creating with `roleKey == "superadmin"` → `"不允许使用系统内置管理员角色标识符!"`;
  - editing where the stored or new `roleKey` is `"superadmin"` → `"不允许修改系统内置管理员角色标识符!"`.
- Data scope `checkRoleDataScope(roleIds)`: non-super-admin must see all rows (`selectRoleCount(roleIds) == roleIds.size()`), else `"没有权限访问部分角色数据！"`. Applied on role getInfo/edit/delete, not on create.
- Status: cannot disable a role with assigned users (`countUserRoleByRoleId > 0` → `"角色已分配，不能禁用!"`) in both `updateRoleBaseInfo` and `updateRoleStatus`.
- Delete: cannot delete a role with assigned users (`"X已分配，不能删除!"`), cannot delete super admin.
- Note: `PUT /system/role/permission` skips unique-name/key checks and bean validation (partial-update body).

## 5. Role-menu write path — exact DB operation sequence

**Create (POST /system/role), one TX:**
1. `checkRoleAllowed`, `checkRoleNameUnique`, `checkRoleKeyUnique` (controller).
2. `INSERT INTO sys_role (...)` — snowflake id, all bo fields, `create_dept/create_by/create_time/update_by/update_time` auto-filled.
3. `INSERT INTO sys_role_menu (role_id, menu_id)` batch — one row per submitted menuId (`Db.saveBatch`).
4. Commit. (No menu existence validation, no parent expansion.)

**Update menus (PUT /system/role/permission), one TX:**
1. `checkRoleAllowed`, `checkRoleDataScope(roleId)` (controller).
2. `UPDATE sys_role SET data_scope=?, menu_check_strictly=?, dept_check_strictly=?, ... WHERE role_id=?` (non-null fields).
3. `DELETE FROM sys_role_menu WHERE role_id = ?` — hard delete of **all** existing links.
4. Batch `INSERT INTO sys_role_menu` for the submitted menuIds (full replacement).
5. `DELETE FROM sys_role_dept WHERE role_id = ?`; batch `INSERT INTO sys_role_dept` for deptIds.
6. Commit; `@CacheEvict(SYS_ROLE_CUSTOM, key=roleId)`; publish `OnlineUserCleanEvent.byRole(roleId)` (forces affected online users to re-login / refresh perms).

**Delete (DELETE /system/role/{ids}), one TX:**
1. `checkRoleDataScope`, per-role `checkRoleAllowed`, `countUserRoleByRoleId > 0` → abort.
2. `DELETE FROM sys_role_menu WHERE role_id IN (...)` (hard).
3. `DELETE FROM sys_role_dept WHERE role_id IN (...)` (hard).
4. `UPDATE sys_role SET del_flag='1' WHERE role_id IN (...)` (logic delete).

`menuCheckStrictly` affects **none** of these writes — always delete-then-insert all rows. The flag only shapes `checkedKeys` on read (see 4.5) and the frontend tree's check-strictly behavior.

## 6. Notable differences vs classic RuoYi-Vue (and within Plus)

- **ORM**: classic RuoYi-Vue = MyBatis XML with hand-written SQL everywhere; **Plus = MyBatis-Plus `BaseMapperPlus` lambda wrappers + MyBatis-Plus-Join (`MPJBaseMapper`) for joins** — `SysRoleMapper.xml` / `SysRoleMenuMapper.xml` are empty stubs.
- **Logic delete**: classic bakes `del_flag = '0'` into every XML WHERE; Plus uses `@TableLogic` so `deleteById` → `UPDATE del_flag='1'` automatically and all queries auto-filter. `sys_role_menu` is hard-deleted in both.
- **IDs**: classic = DB auto-increment; Plus = snowflake IDs with `IdType.INPUT` on join tables.
- **Role update split**: classic has a single `PUT /system/role` → `updateRole` (role row + role_menu rewrite + role_dept rewrite in one TX). **This Plus build splits it**: `PUT /system/role` → `updateRoleBaseInfo` (base fields only, no permission tables) and `PUT /system/role/permission` → `updateRolePermission` (menu + data-scope rewrite). So in classic the menuIds-bearing update and the base-info update are one endpoint; here they are two.
- **roleMenuTreeselect checkedKeys**: classic returns **all** assigned menu ids (parents + children + buttons) unfiltered; **Plus filters out parents-of-other-selected-menus server-side when `menuCheckStrictly == true`** (see 4.5).
- **Batch insert**: classic XML `batchRoleMenu`; Plus `Db.saveBatch` (JDBC batch / rewritten multi-VALUES).
- **Audit columns**: Plus adds `create_dept` and uses bigint user-id `create_by/update_by` (classic: varchar(64) login names).
- **Extra Plus mechanics**: `@RepeatSubmit` idempotency guard on writes; `@CacheEvict`/`@Cacheable` on role & data-scope caches; `OnlineUserCleanEvent` published after role permission/status changes to kick/refresh online users; data-scope enforcement via a SQL plugin (`@DataPermission` on role list queries by `create_dept`/`create_by`).
- **`insertRoleMenu` null-safety**: this vendored copy iterates `role.getMenuIds()` with **no null guard** (NPE if the array is absent); menuIds is effectively required by contract (frontend always sends it).
- `create_time`/`update_time` are `datetime` (MySQL) — no DB default, filled by the app.
