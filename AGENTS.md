# Repository Guidelines

This Kratos service template uses pragmatic DDD naming. This file owns the
layering contract for changes to the template.

## Project structure

```text
api/<domain>/<version>/        Proto sources and generated stubs. Public contract.
cmd/<app>/                     Entrypoint and Wire composition root.
configs/                       Runtime configuration. No secrets.
internal/conf/                 Config proto; generated by `make config`.
internal/server/               HTTP/gRPC construction, middleware, registration.
internal/application/<module>/ Application services: DTO conversion plus
                               cross-domain orchestration (user, access, authn).
internal/crossdomain/<provider>/ Cross-module contracts (ADR 0017 shape).
internal/domain/<module>/      Typed errors at the root; entity/, repository/,
                               and service/ subpackages (user, access, authn).
internal/infra/store/          Shared PostgreSQL, Redis, and transaction clients.
internal/infra/<module>/       Persistence and external adapters.
internal/infra/ent/            Ent schema and generated persistence code.
```

Create a domain directory only when that domain exists. Do not pre-create
empty `knowledge`, `workflow`, `crossdomain`, `bo`, or `vo` directories.

## Layering and dependency rules

Three model shapes flow through the system. Domain owns DOs and port
interfaces; Infra owns POs; Application owns inbound DTO conversion and
cross-domain orchestration (ADR 0020).

```text
client → DTO → Application service ── DTO ↔ DO conversion
                                   ├→ domain service (module-local rules)
                                   ├→ domain port ← Infra adapter → PO → storage
                                   ├→ crossdomain contract (other module)
                                   └→ Transaction.InTx (write flows)

DTO  Data Transfer Object — generated proto request/response.
DO   Domain Object        — pure domain model, no proto or storage tags.
PO   Persistent Object    — storage shape owned by Infra.
```

| Layer | Owns | Speaks at its seam | Never speaks |
|---|---|---|---|
| application | services, DTO conversion, transaction/compensation ordering, cross-domain coordination | DTO ↔ domain values, ports, and crossdomain contracts | Infra, PO, Ent, Redis clients, crossdomain `impl/` |
| crossdomain | consumer-shaped contracts, `model/` snapshots, `impl/` adapters wrapping provider capabilities | contract interfaces over snapshots | DTO, transport, Application services |
| domain | `entity/` DOs, `repository/` ports, `service/` module-local rules, root errors | domain values | DTO, application, infra, crossdomain |
| infra | adapters, PO, storage clients | domain ports, DO ↔ PO | DTO, Application services |
| server | transport construction | Application registrations | translation, business rules, storage |

- Application imports `api/...`, `domain/...`, and `crossdomain/...` contracts.
  Each service may depend on Domain repository/capability ports, crossdomain
  contracts, and the Application-owned transaction port; it never imports
  `infra` or a crossdomain `impl/` package.
- Domain never imports another internal layer. Its service functions may take
  the module's own repository ports as parameters, but they have no
  transaction, cross-module, or transport dependency.
- Infra imports Domain to implement its ports; it does not import Application
  or DTO packages.
- Server constructs transports, applies middleware, and registers Application
  implementations.
- `cmd` is the only composition root and binds concrete infrastructure to
  Application-owned interfaces with Wire.

## Layer responsibilities

### Application

- Keep one package per module: `internal/application/user`,
  `internal/application/access`, and `internal/application/authn`.
- One Application service per proto service, named `<Resource>Application`
  with constructor `New<Resource>Application`. The struct holds the module's
  repository ports, the crossdomain contracts it consumes, the `Transaction`
  port, and a logger; its RPC methods convert DTOs ↔ DOs and own the
  cross-domain orchestration inline: AIP filtering/ordering/pagination and
  field masks, transaction boundaries, compensation, and session revocation.
  Private helper methods may carry a flow when the transport wrapper and the
  orchestration read better apart.
- Keep each Application service a transaction root: do not call one
  Application service from another inside a transaction.
- Place the Application-owned `Transaction` port beside its services. Infra
  provides a concrete manager and `cmd` binds it.
- Intra-domain rules (uniqueness, grant validity, tree assembly, hashing)
  belong in `domain/<module>/service`, never in the Application package.

### Domain

- Keep one package group per bounded context: `internal/domain/user`,
  `internal/domain/access`, and `internal/domain/authn`, each split into
  `entity/`, `repository/`, and `service/` subpackages (ADR 0020), with the
  module's typed errors as the only content of the package root.
- `entity/` owns DOs and value objects with real invariants and their
  behavior. `repository/` owns the port interfaces, their request/response
  shapes, and the `ListOption` family. `service/` owns the module's own rules
  and intra-domain orchestration as stateless functions taking ports as
  parameters.
- Keep models free of proto fields, Ent types, JSON/storage tags, and clients.

### Infrastructure

- `infra/store` owns long-lived PostgreSQL/Redis clients and context-propagated
  transaction machinery.
- `infra/<domain>` implements Domain ports. Constructors return Domain
  interfaces when the port is domain-specific.
- Write adapters join the transaction already propagated through context; they
  do not open their own transaction. Application services wrap every
  PostgreSQL write flow.
- Define a PO only when storage differs from the DO. Convert DO ↔ PO inside
  the adapter and map driver failures at the storage seam.
- Keep Ent-generated code under `infra/ent`; regenerate it, never hand-edit it.

### Server

- Construct HTTP/gRPC servers, apply middleware, and register Application
  implementations.
- No DTO conversion, orchestration, domain rules, or storage access.

## Cross-domain calls

- Domain packages do not invoke each other, import another domain, or import
  `internal/crossdomain`.
- Coordinate cross-domain operations in the caller's Application service.
- Every cross-module call goes through `internal/crossdomain/<provider>`
  regardless of caller count (ADR 0017): `contract.go` holds a consumer-shaped
  minimal interface, `model/` holds flat snapshot types, `impl/` holds adapters
  wrapping the provider's domain capability (never in infra), and a
  mockgen-generated mock package serves tests. Application services receive
  the contract by constructor injection; there is no service locator, and cmd
  stays the only composition root.
- Contracts return small `model/` snapshots, never provider domain objects,
  aggregates, or repositories.
- Pass authenticated identity through `domain/authn.Principal` when no live IAM
  lookup is needed.
- If a module becomes remote, keep the capability interface and provide an
  HTTP/gRPC/queue adapter satisfying it. Use events/outbox for cross-service
  writes.

## Transactions

Application services use their local `Transaction.InTx` port for PostgreSQL
write flows. The Infra transaction manager propagates the transaction through
context, so repositories resolve transaction-aware Ent clients without an
explicit transaction parameter. Pure validation and best-effort prechecks may
run before entering the transaction; authoritative re-reads and writes belong
inside it.

The callback transaction is rooted in one Application service method. Nested
transactions are not supported. Commit-failure compensation is explicit in the
owning service. Repository calls rely on the Application boundary by
convention and tests; they do not enforce or create a transaction themselves.

## Add-a-resource checklist

1. Define Proto DTO/RPC contract in `api/<domain>/<version>/`, then run `make api`.
2. Add the entity DOs to `internal/domain/<domain>/entity/`, the typed errors
   to the module root, the ports to `repository/`, and any module-local rules
   to `service/`.
3. Add the Application service under `internal/application/<domain>/`: DTO
   conversion plus cross-domain orchestration in the RPC methods.
4. Implement ports under `internal/infra/<domain>/`; add PO conversions when
   storage differs.
5. Register service constructors, adapter constructors, port bindings, and
   transports with Wire in `cmd` and the ProviderSets.
6. Run `make all` to regenerate Wire and generated outputs.

## Testing seams

Tests live beside the code they cover (`*_test.go`):

- Application service tests drive the RPC methods through proto DTOs with
  fake Domain ports, fake crossdomain contracts, and a fake transaction —
  exercising DTO conversion, ordering, transactions, and compensation
  together.
- Domain tests exercise entity invariants and the module-local `service/`
  rules without infrastructure.
- Infra tests exercise adapters at storage seams; integration tests may use
  configured PostgreSQL/Redis substitutes.
- Server tests cover middleware and registration, not Application or Domain
  behavior.

## Generation and generated files

Regenerate via `make api`, `make config`, `make all`, or the owning generator.
Never hand-edit `*.pb.go`, `*_grpc.pb.go`, `*_http.pb.go`, Ent-generated files,
or `wire_gen.go`.

## Naming

- Resource: `<Resource>`; collection RPC: `List<Resources>`.
- Application service: `<Resource>Application`; constructor
  `New<Resource>Application`.
- Domain port: `<Resource>Repo` or a capability name such as `AccessChecker`,
  living in `domain/<module>/repository/`.
- Domain rule function: a verb such as `AssertUnique` or `BuildMenuTree`,
  living in `domain/<module>/service/`.
- Infra adapter constructor: `New<Resource>Repo`, returning the Domain port.
- Error values: `Err<Resource><Cause>` in the owning Domain's package root.
- Avoid generic `model`, `common`, `shared`, `bo`, and `vo` packages; the
  ADR 0017 `crossdomain/<provider>/model/` snapshot package is the one
  sanctioned `model` name.

## Commits and security

- Conventional Commits: `feat:`, `fix:`, `refactor:`, `chore(deps):`, `docs:`,
  `test:`. Regenerated files belong in the same commit as their source.
- Never commit real credentials in `configs/config.yaml`.
