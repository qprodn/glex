# Repository Guidelines

This is a Kratos service template organized with pragmatic DDD naming. This
file owns the layering contract agents must follow when changing the template.

## Project structure

```text
api/<domain>/<version>/        Proto sources and generated stubs. Public contract.
cmd/<app>/                     Entrypoint and Wire composition root.
configs/                       Runtime configuration. No secrets.
internal/conf/                 Config proto; generated by `make config`.
internal/server/               HTTP/gRPC construction, middleware, registration.
internal/application/<domain>/ Application operations and DTO ↔ DO conversion.
internal/domain/<domain>/      Domain objects, rules, errors, and port interfaces.
internal/infra/store/          Shared PostgreSQL, Redis, and transaction clients.
internal/infra/<domain>/       Domain-specific persistence and external adapters.
internal/infra/ent/            Ent schema and generated persistence code.
```

Create a domain directory only when that domain exists. Do not pre-create
empty `knowledge`, `workflow`, `crossdomain`, `bo`, or `vo` directories.

## Layering and dependency rules

Three model shapes flow through the system. `domain` owns the DO and port
interfaces; `infra` owns the PO; `application` owns operation orchestration and
the public transport implementation.

```text
client → DTO → application → DO → domain port ← infra adapter → PO → storage
                         └────── domain rules ──────┘

DTO  Data Transfer Object — generated proto request/response.
DO   Domain Object        — pure domain model, no proto or storage tags.
PO   Persistent Object    — storage shape owned by infra.
```

| Layer | Owns | Speaks at its seam | Never speaks |
|---|---|---|---|
| application | operations and orchestration | DTO ↔ DO | PO, Ent, Redis, infra implementation |
| domain | DO, rules, errors, ports | DO | DTO, PO, application, infra |
| infra | adapters, PO, storage clients | domain ports, DO ↔ PO | DTO, application |
| server | transport construction | application registrations | translation, business rules, storage |

- `application` imports `api/...` and `domain/...`; never `infra`.
- `domain` never imports another internal layer. Repository and external
  capability interfaces are declared at this inward seam.
- `infra` imports `domain` to implement its interfaces; never `application`
  or DTO packages.
- `server` constructs transports, applies middleware, and registers
  Application implementations.
- `cmd` is the only composition root and wires all adapters with Wire.

Any dependency crossing these arrows in the wrong direction is a layering
bug. Fix the design instead of adding the import.

## Layer responsibilities

### Application

- One package per domain, for example `internal/application/iam`.
- Implement generated Kratos service-server interfaces.
- Parse and validate DTOs, AIP filtering/ordering/pagination, and field masks.
- Convert DTO ↔ DO at request and response sites.
- Own operation ordering, transactions, authorization checks, compensation,
  and coordination across domain modules.
- Depend on narrow domain ports. Never construct or type-assert an infra
  adapter and never import Ent, Redis, or storage-specific types.
- Name entry types `<Resource>Application`; name constructors
  `New<Resource>Application`.

Application packages may use internal implementation seams such as a usecase
type for focused tests. These are implementation details of the package, not a
new architectural layer.

### Domain

- One package per bounded context, for example `internal/domain/iam`.
- Own DOs, value objects with real invariants, pure policies, typed errors,
  repository ports, and external-capability ports.
- Keep related concepts as files in the domain package. Do not mechanically
  split `entity`, `repository`, `service`, `bo`, or `vo` subpackages.
- Keep models free of proto fields, Ent types, JSON/storage tags, and clients.
- Own `ListOption` helpers so callers can compose reads without exposing a
  storage query language.

### Infrastructure

- `infra/store` owns long-lived PostgreSQL/Redis clients and transaction
  propagation. Domain adapters receive the shared store through constructors.
- `infra/<domain>` implements that domain's repository and external-capability
  ports. Constructors return the domain interface, never the concrete type.
- Define a PO only when the storage shape diverges from the DO. PO and driver
  types never leave Infra.
- Convert DO ↔ PO inside the adapter with free conversion functions.
- Translate filters/orderings into driver queries and map driver failures to
  domain errors.
- Keep Ent-generated code under `infra/ent`; regenerate it, never hand-edit it.

### Server

- Construct HTTP/gRPC servers, apply middleware, and register Application
  implementations.
- No DTO conversion, operation orchestration, domain rules, or storage access.

## Cross-domain calls

- Domain packages do not invoke each other or import another domain's
  implementation.
- Coordinate cross-domain operations in the caller's Application package.
- For one caller, define the smallest required interface beside that caller
  and inject an in-process adapter with Wire.
- Pass authenticated identity through `domain/iam.Principal` when no live IAM
  lookup is needed.
- Promote a repeated, stable contract to `internal/crossdomain/<provider>` only
  after at least two callers need it. Return small snapshots, not another
  domain's full aggregate or repository.
- If a module becomes remote, keep the same interface and provide an
  HTTP/gRPC/queue adapter in Infra. Use events/outbox for cross-service writes.

## Transactions

Application operations wrap multi-write flows with `Transaction.InTx` through
the domain port in `internal/domain/iam/tx.go`; `infra/store` implements it with
the generated Ent database wrapper. Repositories resolve transaction-aware
clients from the propagated context, so nested calls join the outermost
transaction and receive no explicit transaction parameter.

Security-relevant Redis writes run last inside the transaction closure so a
Redis failure rolls PostgreSQL back. Login credential issuance compensates a
commit failure. PostgreSQL advisory locks remain internal to `infra/iam`.

## Add-a-resource checklist

1. Define the Proto DTO/RPC contract in `api/<domain>/<version>/`, then run
   `make api`.
2. Add the DO, rules, errors, and required ports under
   `internal/domain/<domain>/`.
3. Add the operation and DTO conversions under
   `internal/application/<domain>/`.
4. Implement ports under `internal/infra/<domain>/`; add PO conversions when
   the storage shape differs.
5. Register constructors in the domain-specific Application/Infra ProviderSet
   and transports in `internal/server`.
6. Run `make all` to regenerate Wire and other generated outputs.

## Testing seams

Tests live beside the code they cover (`*_test.go`):

- Application tests exercise observable operations with fake domain ports.
- Domain tests exercise pure rules and invariants without infrastructure.
- Infra tests exercise adapters at storage seams; integration tests may use
  local PostgreSQL/Redis substitutes or explicitly configured stores.
- Server tests cover middleware and registration, not domain behavior.

The module interface is the test surface. Do not duplicate tests against
internal pass-through helpers after the Application operation is covered.

## Generation and generated files

Regenerate via `make api`, `make config`, `make all`, or the owning generator.
Never hand-edit `*.pb.go`, `*_grpc.pb.go`, `*_http.pb.go`, Ent-generated files,
or `wire_gen.go`.

## Naming

- Resource: `<Resource>`; collection RPC: `List<Resources>`.
- Application entry: `<Resource>Application`.
- Domain port: `<Resource>Repo` or a capability name such as `AccessChecker`.
- Infra adapter constructor: `New<Resource>Repo`, returning the domain port.
- Error values: `Err<Resource><Cause>` in the owning domain.
- Avoid generic `model`, `common`, `shared`, `bo`, and `vo` packages.

## Commits and security

- Conventional Commits: `feat:`, `fix:`, `refactor:`, `chore(deps):`, `docs:`,
  `test:`. Regenerated files belong in the same commit as their source.
- Never commit real credentials in `configs/config.yaml`.
